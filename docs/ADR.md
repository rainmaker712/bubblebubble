# BubbleBubble Architecture Decision Records

> 상태: 제안(Proposed)  
> 최초 작성: 2026-10-18  
> 최종 조사: 2026-10-18  
> 대상: 브라우저에서 실행되는 고정 화면형 2D 버블 액션 게임

## 1. 문서 목적

이 문서는 1986년작 **Bubble Bobble**의 핵심 재미에 포차코와 마이멜로디를 결합한 개인용 웹 게임 `BubbleBubble`의 제품 범위와 기술 결정을 기록한다. 플레이어는 **포차코(1P)**와 **마이멜로디(2P)**이고, 적은 Bubble Bobble의 주인공 공룡 **버블룬·보블룬의 귀신 버전**이다. 이 구성은 아이와 같은 컴퓨터에서 즐기는 비공개 로컬 프로토타입에만 사용한다.

구현 중 결정이 바뀌면 기존 내용을 지우지 않고 해당 ADR을 `대체됨(Superseded)`으로 표시한 뒤 새 ADR을 추가한다.

## 2. 조사에서 확인한 핵심

- Taito는 원작을 1986년에 출시된 100스테이지 액션 게임으로 소개한다. 기본 동사는 이동, 점프, 거품 발사이며, 거품으로 적을 가두고 터뜨려 스테이지를 정리한다.
- 거품은 무기만이 아니라 발판과 이동 수단으로도 작동한다. 이 다목적성이 게임의 가장 중요한 차별점이다.
- 원작 아케이드판은 2인 동시 플레이, 좌우 이동과 2버튼 조작, 256×224 래스터 화면을 사용했다.
- 고정 화면 안의 플랫폼 배치, 거품의 상승 경로, 적 배치가 서로 맞물려 액션과 퍼즐을 동시에 만든다.
- 여러 적을 연쇄로 제거할수록 더 큰 보상을 주는 구조가 숙련 플레이와 반복 플레이의 동기가 된다.

`BubbleBubble`은 아래 플레이 원칙을 중심으로 난이도와 테마가 달라지는 10개 스테이지를 구현한다.

1. **3초 안에 이해되는 규칙**: 쏘고, 가두고, 터뜨린다.
2. **하나의 도구, 여러 용도**: 거품은 공격·발판·연쇄 폭발 수단이다.
3. **짧고 밀도 높은 판**: 제한 시간은 60초를 기준으로 스테이지별 70~40초이며, 시간이 끝나면 실패 대신 무적 고래 두개골 귀신이 출현해 빠른 클리어를 압박한다.
4. **우연보다 읽을 수 있는 규칙**: 이동, 기류, 생성 조건은 관찰과 학습이 가능해야 한다.
5. **점수와 협동이 다시 할 이유가 된다**: 빠른 클리어뿐 아니라 연쇄 제거와 동료 구조를 보상한다.

## 3. 제품 범위

### MVP 플레이 루프

```text
타이틀 → 캐릭터/입력 선택 → 스테이지 시작
  → 이동·점프·거품 발사
  → 적 포획 → 제한 시간 안에 거품 파괴
  → 보상 획득·연쇄 점수
  → 모든 공룡 귀신 제거 → 과일·간식 획득
  → 또는 E·X·I·T 완성 → 보너스 조기 클리어
  → 다음 스테이지 또는 10개 스테이지 완료/생명 소진 → 결과 화면
```

### MVP에 포함

- 데스크톱 브라우저 싱글 플레이와 같은 기기의 2인 로컬 협동
- 스테이지 10개: 기존 5개 테마와 `심해 신전`, `장난감 공장`, `얼음 궁전`, `화산 심장`, `우주 성채`
- 1P 포차코와 2P 마이멜로디(초기 능력치는 동일)
- 적 2종: 순찰하는 버블룬 귀신과 추적하는 보블룬 귀신, 스테이지별 색·장식 변형
- 일반 거품, 포획 거품, 터지는 상태, 수명 만료 상태
- 시간 종료 후 출현하는 제거 불가능한 비행형 고래 두개골 귀신과 위험 모드 음악·화면 효과
- 거품 밟기, 화면 하단에서 상단으로 이어지는 세로 랩(wrap), 스테이지별 기류
- 딸기·바나나·쿠키 점수 아이템, 물·불·신발·방패·비행 구름 강화 아이템, 희귀 EXIT 알파벳 보너스, 생명·점수·시간 HUD
- 키보드와 표준 Gamepad API 입력, 일시정지, 음소거
- 최고 점수와 설정의 로컬 저장

### MVP에서 제외

- 열한 번째 이후 스테이지와 원작의 숨겨진 엔딩/치트/아이템 테이블 재현
- 온라인 실시간 협동, 계정, 서버 저장, 전 세계 리더보드
- 모바일 터치 조작과 세로 화면 최적화
- 보스전, 스테이지 에디터, 사용자 제작 콘텐츠
- 공개 URL 배포, 앱스토어 등록, 판매, 광고, 제3자 공유
- 원작 ROM·음원·스테이지 데이터의 추출 또는 포함

## 4. 게임플레이 기준 사양

| 영역 | MVP 결정 | 초기 튜닝값(데이터로 분리) |
|---|---|---|
| 이동 | 좌우 가속 + 감속, 공중 제어 허용 | 최대 속도 80 px/s |
| 점프 | 누르는 길이에 따라 높이가 달라지는 점프 | 초기 속도 -170 px/s, 코요테 타임 80 ms |
| 거품 발사 | 바라보는 방향으로 전진한 뒤 기류를 따라 상승 | 쿨다운 280 ms, 포획 전 수명 4 s |
| 적 포획 | 발사 직후 전진 중인 거품을 적에게 직접 맞히면 포획 | 포획 제한 5 s |
| 적 제거 | 플레이어 또는 다른 거품이 포획 거품을 터뜨리면 제거 | 기본 100점 |
| 콤보 | 짧은 판정 창 안에 함께 터진 포획 거품 수로 계산 | 1/2/3/4+마리: ×1/×2/×4/×8 |
| 거품 밟기 | 점프 입력 중 거품 위에 닿으면 반동 점프 | 반동 속도 -145 px/s |
| 피격 | 적과 접촉하면 생명 감소 후 재등장 무적 | 생명 3, 무적 3 s |
| 타임 압박 | 시간이 끝나면 적이 분노하고 무적 고래 두개골 귀신이 추격 | 스테이지별 70~40 s, 이후 플레이 지속 |
| 클리어 | 모든 적 제거 후 간식 획득 또는 EXIT 완성 | EXIT 완성 시 5,000점 보너스 |
| 강화 아이템 | 거품 연사·고속화, 이동·점프 강화, 1회 공격 방어, 비행 | 물·불·신발 12 s, 방패 15 s 내 1회, 구름 10 s |
| EXIT 드롭 | 적 제거 시 낮은 확률로 다음 글자 등장 | 처치당 22%, E→X→I→T 순서 |

수치는 재미 검증 전의 시작점일 뿐이다. `src/game/config/balance.ts` 같은 단일 설정 파일에서 관리하고 플레이테스트 결과로 조정한다.

### 입력 기본값

| 동작 | 1P 키보드 | 2P 키보드 | 게임패드 |
|---|---|---|---|
| 이동 | `A` / `D` | `←` / `→` | D-pad / 왼쪽 스틱 |
| 점프 | `W` 또는 `Space` | `↑` | South 버튼 |
| 거품 | `F` | `/` | West 버튼 |
| 일시정지 | `Esc` | `Esc` | Start |
| 이어하기 | `C` | `C` | 추후 지정 |

키보드 고스팅을 고려해 키 재설정을 지원하고, 연결된 게임패드를 우선 권장한다.

## ADR-001: 비공개 개인용 크로스오버 프로토타입으로 만든다

**상태**: 채택  
**결정**: 포차코와 마이멜로디를 플레이어로, 버블룬·보블룬을 공룡 귀신 적으로 사용한다. 결과물은 개발자와 아이가 같은 컴퓨터에서 실행하는 로컬 프로토타입으로 한정한다. 저장소에는 직접 그린 임시 이미지 또는 도형 플레이스홀더만 두며, 웹에서 찾은 이미지를 내려받아 포함하지 않는다.  
**이유**: 사용자가 원하는 가족용 캐릭터 구성을 가장 작은 범위에서 빠르게 검증하기 위함이다. Sanrio는 캐릭터 이름과 이미지를 자사 지식재산으로 안내하고, Taito도 Bubble Bobble의 IP 소유권을 밝히고 있으므로 공개·공유·판매로 범위가 바뀌면 별도 허락 검토가 필요하다.  
**트레이드오프**: 로컬에서는 원하는 캐릭터 경험을 얻지만, 현재 결과물을 그대로 배포하거나 포트폴리오에 공개할 수 없다. 공개 버전이 필요하면 라이선스를 확보하거나 캐릭터와 에셋을 오리지널 디자인으로 교체한다.  
**검증**: 빌드와 문서에 `PRIVATE_LOCAL_PROTOTYPE` 표시를 두고, 배포 스크립트·공개 호스팅 설정·외부 분석 도구를 만들지 않는다.

## ADR-002: TypeScript + Vite + Phaser 4를 사용한다

**상태**: 채택  
**결정**: 게임 런타임은 TypeScript strict mode, Vite, Phaser 4.x를 사용하고 설치 시 정확한 버전을 lockfile에 고정한다. UI가 복잡해질 때만 DOM 레이어를 추가하며, 게임 플레이는 Phaser Scene 안에서 처리한다.  
**이유**: Phaser의 Arcade Physics는 직사각형/원 충돌, 중력, 타일맵, 월드 랩과 고정 스텝을 제공하여 이 게임 규모에 맞다. `pixelArt` 설정도 최근접 보간과 정수 픽셀 렌더링을 한 번에 제공한다. Vite는 별도 서버 프레임워크 없이 정적 배포가 가능하다.  
**트레이드오프**: Phaser API와 수명주기에 결합된다. 정밀한 곡면 물리는 직접 보완해야 하지만, 거품 충돌은 원형 오버랩 판정으로 충분하다.  
**기각안**: 순수 Canvas는 충돌·입력·오디오·에셋 수명주기를 모두 직접 만들어야 한다. React를 게임 루프에 사용하는 방식은 프레임 단위 상태와 DOM 렌더링 모델이 맞지 않는다.

## ADR-003: 논리 해상도 256×224와 픽셀 퍼펙트 렌더링을 사용한다

**상태**: 채택  
**결정**: 월드의 논리 좌표계는 256×224로 두고, 브라우저에서는 화면에 맞는 정수 배율로 확대한다. `pixelArt: true`, `roundPixels: true`, nearest-neighbor 필터를 사용한다. 16:9 화면의 남는 영역은 배경/조작 안내에 사용하고 플레이필드는 늘이지 않는다.  
**이유**: 원작 하드웨어의 256×224 구성을 참고하면 고정 화면의 밀도를 빠르게 설계할 수 있고, 16px 타일 기준 16×14 셀로 계산하기 쉽다.  
**트레이드오프**: 작은 원본 캔버스 때문에 텍스트와 UI 표현이 제한된다. HUD는 안전 영역을 미리 예약하고, 접근성 텍스트는 캔버스 밖 DOM에도 제공한다.  
**검증**: 1280×720, 1920×1080, 2560×1440에서 픽셀이 흐려지지 않고 플레이필드가 잘리지 않아야 한다.

캐릭터·적·강화 아이템은 논리 표시 크기의 2배 해상도로 Canvas 텍스처를 생성하고 선형 필터로 축소 표시한다. Arcade Physics 충돌 크기는 원본 텍스처 픽셀이 아닌 논리 표시 크기에 맞춰 별도로 2배 보정한다. 적에게는 반복 스케일 애니메이션을 적용하지 않으며, 포획 상태에서만 명시적인 작은 표시 크기를 사용한다.

## ADR-004: 렌더링과 시뮬레이션을 분리하고 60 Hz 고정 스텝을 사용한다

**상태**: 채택  
**결정**: 입력을 `InputFrame`으로 정규화하고 게임 규칙은 60 Hz 고정 스텝에서 처리한다. 렌더 프레임과 물리 프레임을 분리하며, 탭 비활성화 후 누적 시간은 상한을 두고 일시정지한다. 게임 규칙의 난수는 seed 가능한 PRNG를 사용한다.  
**이유**: 프레임률에 따라 점프, 거품 수명, 콤보 판정이 달라지는 문제를 막고, 향후 리플레이·온라인 동기화의 기반을 만든다.  
**트레이드오프**: 구현이 단순 delta-time 방식보다 복잡하고, 저사양 기기에서 따라잡기 정책이 필요하다.

## ADR-005: 플레이어·적·거품을 명시적 상태 머신으로 모델링한다

**상태**: 채택  
**결정**:

```text
Player: SPAWN → IDLE/RUN ↔ JUMP/FALL → HIT → RESPAWN | DEAD
Enemy:  SPAWN → ACTIVE → CAPTURED → ENRAGED | DEFEATED
Bubble: FIRED → DRIFTING → CAPTURING/CAPTURED → POPPING | EXPIRED
Stage:  INTRO → PLAYING → CLEARING | FAILED → TRANSITION
```

상태 전이는 도메인 이벤트(`EnemyCaptured`, `BubblePopped`, `ComboResolved`, `StageCleared`)를 발생시킨다. 점수, 오디오, 파티클은 이벤트를 구독하되 충돌 콜백 안에서 서로를 직접 수정하지 않는다.  
**이유**: “포획됐지만 아직 제거되지 않은 적”처럼 시각 상태와 게임 상태가 다른 경우를 명확히 다룰 수 있다.  
**트레이드오프**: 작은 프로토타입보다 파일과 타입 수가 늘어나지만, 중복 점수·이중 제거·콜백 순서 버그를 줄인다.

## ADR-006: 스테이지를 데이터로 정의하고 기류를 별도 레이어로 둔다

**상태**: 채택  
**결정**: 스테이지는 Tiled JSON 또는 동등한 저장소 내 JSON으로 관리한다. 충돌 타일, 장식, 플레이어 스폰, 적 스폰, 아이템 스폰, 기류 벡터를 분리한다.

```ts
type StageDefinition = {
  id: string;
  title: string;
  layout: string[];
  playerSpawns: Array<{
    character: 'pochacco' | 'my_melody';
    tile: { x: number; y: number };
  }>;
  enemies: Array<{
    kind: 'ghost_bubblun' | 'ghost_bobblun';
    tile: { x: number; y: number };
  }>;
  items: Array<{
    kind: 'water' | 'fire' | 'shoes' | 'shield' | 'cloud';
    tile: { x: number; y: number };
  }>;
  airflow: Array<{
    tileRect: { x: number; y: number; width: number; height: number };
    direction: { x: -1 | 0 | 1; y: -1 | 0 | 1 };
  }>;
  rules: { timeLimitSeconds: number; nextStageId: string | null };
};
```

**이유**: 거품 경로는 레벨 디자인의 일부이므로 코드에 숨기지 않고 편집·시각화·검증할 수 있어야 한다.  
**트레이드오프**: 편집 파이프라인과 스키마 검증이 필요하다.  
**검증**: 스폰 지점이 벽 내부인지, 모든 적이 유효한 플랫폼/비행 영역에 있는지, 플레이어가 모든 영역에 도달 가능한지를 CI에서 검사한다.

## ADR-007: MVP는 로컬 협동까지만 제공한다

**상태**: 채택  
**결정**: 1P와 2P는 같은 시뮬레이션과 화면을 공유한다. 한 플레이어가 모든 생명을 잃어도 다른 플레이어가 스테이지를 끝낼 때까지 관전한다. 다시 하기를 선택하면 두 캐릭터 모두 생명 3으로 시작한다. 온라인 협동은 MVP 이후 별도 ADR로 결정한다.  
**이유**: 실시간 플랫폼 액션의 온라인화에는 입력 지연, 예측, 롤백, 세션 복구, 치트 대응이 필요하다. 핵심 조작감이 검증되기 전에 서버 범위를 추가하지 않는다.  
**트레이드오프**: 원격 친구와 바로 플레이할 수 없다. 대신 고정 스텝, 직렬화 가능한 입력, seed 난수로 향후 롤백 또는 입력 동기화를 준비한다.

## ADR-008: Python 백엔드는 가능하지만 샘플에서는 실행하지 않는다

**상태**: 채택  
**결정**: 브라우저 게임은 TypeScript + Phaser가 담당한다. Python이 필요한 시점에는 **FastAPI**를 별도 `backend/` 서비스로 추가해 점수 저장, 가족용 플레이 기록, 스테이지 API와 WebSocket 세션을 담당하게 한다. 현재 3스테이지 로컬 샘플은 `localStorage`만 사용하며 Python 프로세스는 Vite 실행 보조에만 사용한다.  
**이유**: Python 백엔드 사용은 충분히 가능하고 FastAPI는 HTTP와 WebSocket을 모두 지원한다. 그러나 물리·입력·렌더링을 서버에 옮기면 조작 지연과 운영 복잡도만 늘어난다.  
**트레이드오프**: 지금은 다른 컴퓨터와 기록을 공유할 수 없다. 대신 설치와 실행이 단순하고 인터넷 연결 없이 아이와 바로 플레이할 수 있다.  
**향후 구조**:

```text
Browser: TypeScript + Phaser
   ├─ 게임 루프, 입력, 충돌, 화면, 소리
   └─ REST/WebSocket (필요할 때만)
          ↓
Python: FastAPI
   ├─ 점수/플레이 기록 API
   ├─ 스테이지 데이터 API
   └─ 온라인 세션(후속 범위)
          ↓
SQLite(개인용) → PostgreSQL(공개 서비스 전환 시)
```

## ADR-009: 저장은 버전이 있는 localStorage로 시작한다

**상태**: 채택  
**결정**: 최고 점수, 최고 콤보, 볼륨, 키 설정을 `bubblebubble.save.v1`에 저장한다. 런 중인 게임 저장은 지원하지 않는다. 데이터는 런타임 스키마 검증 후 읽고, 손상 시 안전한 기본값으로 복구한다.  
**이유**: 계정과 백엔드 없이 정적 호스팅할 수 있다.  
**트레이드오프**: 기기 간 동기화와 신뢰 가능한 리더보드는 제공하지 못한다.

## ADR-010: 오디오와 시각 효과는 게임 상태에서 분리한다

**상태**: 채택  
**결정**: 첫 사용자 입력 이후 오디오 컨텍스트를 시작하고, `master/music/sfx` 채널을 분리한다. BGM은 자체 제작 또는 라이선스가 확인된 트랙만 사용한다. 화면 흔들림·섬광·파티클은 설정에서 줄이거나 끌 수 있고 게임 판정에는 영향을 주지 않는다.  
**이유**: 브라우저 자동 재생 정책과 접근성 요구를 만족하고, 효과 때문에 테스트 결과가 변하지 않게 한다.  
**트레이드오프**: 오디오 매니저와 효과 설정 계층이 추가된다.

## ADR-011: 테스트 가능한 순수 규칙 코어를 둔다

**상태**: 채택  
**결정**: 점수, 콤보, 상태 전이, 스폰, 타이머는 Phaser 객체와 분리한 순수 TypeScript 모듈로 구현한다. Vitest로 단위 테스트하고, Playwright로 타이틀→스테이지→클리어의 브라우저 흐름을 검사한다.  
**이유**: 물리/렌더링이 없어도 엣지 케이스를 빠르고 결정적으로 재현할 수 있다.  
**필수 테스트**:

- 포획 제한 시간이 끝나면 적이 `ENRAGED`로 돌아온다.
- 하나의 적은 한 번만 제거되고 한 번만 점수를 준다.
- 같은 판정 창의 연쇄 제거 배수가 정확하다.
- 1P/2P가 동시에 같은 거품을 터뜨려도 결과가 한 번만 적용된다.
- 일시정지 중 타이머, AI, 거품 수명이 진행되지 않는다.
- 다른 렌더 FPS에서도 같은 입력 로그와 seed는 같은 결과를 낸다.

**트레이드오프**: 초기에 어댑터와 이벤트 타입을 설계해야 한다.

## 6. 스테이지 설계 원칙

- 한 스테이지에는 먼저 하나의 학습 목표만 둔다: 포획, 연쇄, 거품 밟기, 세로 랩, 기류 순서로 소개한다.
- 첫 시도에서 적어도 하나의 안전한 포획 기회를 제공한다.
- 막다른 공간은 의도된 위험/보상이 없는 한 만들지 않는다.
- 콤보를 노릴 집결 지점과, 초보자가 한 마리씩 처리할 안전 경로를 함께 둔다.
- 기류는 배경 입자나 흔들리는 장식으로 방향을 암시한다. 보이지 않는 규칙만으로 실패하게 하지 않는다.
- 적 수를 늘리는 것보다 지형·기류·적 조합으로 난도를 높인다.

### 샘플 스테이지 01 — 달빛 놀이터

실제 데이터는 [`docs/samples/stage-01.json`](./samples/stage-01.json)에 둔다. `#`은 발판, `P`는 포차코, `M`은 마이멜로디, `G`는 버블룬 귀신, `B`는 보블룬 귀신의 시작 위치를 뜻한다. 아래 그림은 읽기 쉬운 설명용이며 JSON의 충돌 맵과 스폰 데이터가 실제 기준이다.

```text
################
#..............#
#...####.......#
#..........###.#
#..............#
#..####........#
#..............#
#.......####...#
#..............#
#....###.......#
#..G........B..#
#.###......###.#
#.P..........M.#
################
```

| 항목 | 내용 |
|---|---|
| 학습 목표 | 이동, 점프, 거품 발사, 포획한 거품 터뜨리기 |
| 플레이어 | 왼쪽 포차코(1P), 오른쪽 마이멜로디(2P) |
| 적 | 순찰·추적형 공룡 귀신 4마리 |
| 기류 | 중앙 상승기류, 화면 위쪽의 약한 왼쪽 기류 |
| 제한 시간 | 1스테이지 70초, 남은 시간 30초부터 공룡 귀신 분노, 0초에 무적 해골 귀신 고래 출현 |
| 클리어 | 모든 공룡 귀신 제거 후 간식 획득 또는 EXIT 네 글자 완성 |
| 실패 | CONTINUE 입력 없이 두 플레이어의 생명이 모두 0이 됨. 제한 시간 종료만으로는 실패하지 않음 |
| 다음 스테이지 | 간식을 획득하면 `별빛 계단`으로 진행 |

두 플레이어가 한 귀신을 동시에 터뜨려도 제거와 점수는 한 번만 적용한다. 혼자 플레이할 때는 선택하지 않은 캐릭터를 생성하지 않고 적의 체력이나 수를 바꾸지 않는다.

모든 플레이어의 생명이 소진되면 10초간 시뮬레이션과 타이머를 멈추고 `C` 키 입력을 기다린다. 이어하기를 선택하면 현재 점수, 남은 적과 드롭 아이템을 유지하고 각 플레이어의 생명만 3으로 회복한다. 바닥 구멍으로 빠진 플레이어·적·드롭 아이템은 화면 위에서 다시 등장하며, 천장에 도달한 포획 거품은 화면 아래로 이어진다.

## 7. 구현 로드맵과 완료 조건

### M0 — 1주: 조작감 프로토타입

- 플레이어 이동/점프, 플랫폼 충돌, 거품 발사와 상승
- 임시 도형 에셋 1개 스테이지
- **완료 조건**: 키보드와 게임패드로 60초 동안 끼임 없이 이동하고 거품을 밟을 수 있다.

### M1 — 1~2주: 핵심 전투 버티컬 슬라이스

- 적 1종, 포획/탈출/분노, 거품 파괴, 점수와 클리어
- 순수 규칙 단위 테스트와 디버그 오버레이
- **완료 조건**: 타이틀부터 결과 화면까지 한 판을 반복 플레이할 수 있고 필수 상태 전이 테스트가 통과한다.

### M2 — 1주: 10개 스테이지와 로컬 협동

- 공룡 귀신 2종과 스테이지별 10개 외형, 10개 테마 스테이지, 기류, 점수용 과일·간식, 물·불·신발·방패·구름 강화, 희귀 EXIT 보너스, 고래 두개골 귀신, 2P
- 난이도 플레이테스트 및 밸런스 데이터화
- **완료 조건**: 아이가 간단한 화면 안내만 보고 스테이지를 완료할 수 있고, 한 판이 1~3분 안에 끝난다.

### M3 — 선택: 가족용 완성도 개선

- 직접 만든 로컬 캐릭터 이미지, 사운드, 설정, 접근성, 저장
- 사용하는 컴퓨터의 브라우저에서 성능·입력·E2E 확인
- **완료 조건**: 대상 컴퓨터에서 인터넷 없이 실행되고, 60 FPS 목표와 치명적 오류 0건을 만족한다.

### M4 — 범위를 넓힐 때만 검토

- Python FastAPI 점수/플레이 기록 API
- 온라인 리더보드: 서버 검증 가능한 점수 이벤트/리플레이부터 설계
- 온라인 협동: WebRTC/WebSocket, 입력 지연 측정 후 lockstep/rollback 비교 ADR 작성
- 추가 스테이지, 보스, 모바일 입력, 에디터
- 공개 또는 공유 전 Sanrio와 Taito 캐릭터를 사용할 수 있는 권한 확인

### 프로젝트 아트 방향

- 1P 포차코는 흰 몸과 검은 귀, 2P 마이멜로디는 분홍 후드와 긴 귀로 즉시 구분한다.
- 버블룬 귀신은 초록 공룡 실루엣에 반투명 꼬리, 보블룬 귀신은 파랑 공룡 실루엣에 반투명 꼬리를 붙인다.
- 피격과 제거는 무섭거나 폭력적으로 보이지 않게 별과 작은 거품으로 사라지는 연출을 사용한다.
- 배경은 아이에게 친숙한 밤의 놀이터로 하고, 어두운 배경에서도 캐릭터의 얼굴과 발판이 선명해야 한다.
- 한 스테이지의 주요 색은 배경 1, 플랫폼 2, 위험 1, 상호작용 1로 제한한다.
- 외부 사이트의 공식 이미지를 게임 에셋으로 복사하지 않고, 로컬 플레이용 픽셀 이미지를 직접 그리거나 단순 도형으로 표현한다.

## 12. 미해결 결정

다음 항목은 프로토타입 데이터가 생긴 뒤 별도 ADR로 결정한다.

- 거품 밟기를 완전 자동으로 할지, 점프 버튼을 누른 경우에만 할지
- 팀 생명 공유와 개인 생명 중 어느 쪽이 협동 플레이에 더 명확한지
- 고득점 리플레이를 저장할 때 전체 스냅샷과 입력 로그 중 무엇을 사용할지
- 온라인 리더보드의 부정 점수 검증 범위
- Python 백엔드를 실제로 추가할 만큼 공유할 플레이 기록이 필요한지
- 공개 버전으로 확장할 경우 라이선스 확보와 오리지널 캐릭터 교체 중 어느 방향을 선택할지
